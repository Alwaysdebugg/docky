# F54 · 企业治理:RBAC · 审计 · 合规 · 密钥防护

> 一句话:给 docky 装上企业级信任底座——基于角色的读写权限、完整审计、合规留存策略、以及写入时的密钥扫描脱敏——让组织敢把知识库交给它。

## 战略定位

要成为组织级旗舰(而非个人工具),docky 必须**让企业敢用**:谁能读/写/管哪个项目要可控,所有动作要可审计,留存要合规,且知识库**绝不能变成密钥泄漏渠道**(agent 很可能把 API key 写进文档)。这是从"个人 vault"到"团队/组织知识平台"的信任门槛。

## 背景与痛点

- F15 是**项目读作用域**(grant 模型),但**没有角色/身份/权限分层**(读者 vs 作者 vs 维护者 vs 管理员)。
- 审计只有 git author(F08),**没有"谁读了/改了/授权了什么"的统一可导出审计**。
- **没有合规留存**(按策略自动过期/脱敏),也**没有密钥扫描**——agent 写入可能夹带凭据,成为泄漏面。

## 目标 / 非目标

**目标**
- **RBAC**:per 项目/工作区的角色(reader/author/maintainer/admin),在**核心层 + MCP** 强制(客户端不可越权)。
- **审计**:对 读/写/授权/删除 等动作记不可篡改审计日志(F37 原子追加),可导出(F35 JSON)。
- **合规留存**:按策略自动过期/归档/脱敏(在 F03 生命周期之上加 policy 引擎)。
- **密钥防护**:写入时扫描凭据(API key/token/私钥),命中则拦截或脱敏(挂在 F20 写路径),并由 F19/F53 巡检存量。

**非目标**
- 不自建身份提供商(对接组织既有 SSO/身份;docky 侧做映射与强制)。
- 不取代企业 DLP,但提供面向文档库的最小必要防护。

## 用户故事

- 作为管理员,我设 agent 身份为某项目的 `author`(可写不可管),并能导出"上周谁改了什么"的审计。
- 作为安全,我确信 agent 把 `sk-...` 写进文档时会被当场拦下并脱敏。

## 交互设计

```
$ docky role set agent@ci my-app author
$ docky audit --since 7d --json | jq      # 可导出审计
$ docky write ...   # 命中密钥
✗ 检测到疑似密钥(OpenAI key),已拦截。--redact 可脱敏后写入。
```

## 技术落点

- `src/governance.ts`:角色/策略模型;在 core 读写与 `mcp.ts` 入口强制(服务端裁决)。
- 审计:append-only 日志(F37 原子),`docky audit`(F35 JSON 导出)。
- 留存:policy 引擎叠加 F03 生命周期;密钥扫描器挂 F20 写路径,存量交 F19/F53。
- 身份:对接 SSO/外部身份的映射钩子。

## 验收标准

- [ ] 角色权限在核心层 + MCP 强制(reader 不能写、author 不能管等)。
- [ ] 读/写/授权/删除 有不可篡改审计,可 `--json` 导出。
- [ ] 合规留存策略可配并生效(过期/归档/脱敏)。
- [ ] 写入密钥被拦截或脱敏;存量可经巡检(F19/F53)。
- [ ] 默认无角色配置时行为不变(向后兼容);治理逻辑有单测含越权负例。

## 衡量指标

- 越权访问/写入被拒比例(应 100%)。
- 写入密钥泄漏事件归零;审计可满足合规抽查。

## 风险与依赖

- 安全必须服务端强制,客户端不可绕过;默认关闭、最小授权。
- 依赖 F15(作用域)/F08(历史)/F18(配置)/F37(审计原子)/F20(写拦截)/F19·F53(存量)。

## 与其他提案的关系(迭代递进)

- 在 **F15 的读作用域** 之上加 **角色 + 审计 + 合规 + 密钥防护**,是组织级采纳的信任前提。
- 与 **F31 团队同步 / F51 多 agent** 配套:多人多 agent 共享时,治理才使其安全可控。
