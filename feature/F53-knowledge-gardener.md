# F53 · 知识园丁:矛盾检测与自动改进

> 一句话:让 docky 主动**把知识库越养越好**——发现互相矛盾的文档、重复的内容、缺失的覆盖,并给出可审阅的改进建议,而不是只做结构体检(F19)。

## 战略定位

旗舰级知识库不能只"不报错",还要**语义上越来越健康**。F19 是结构 lint(缺字段/断链/陈旧),但**两篇设计互相打架、同一主题三处重复、关键代码区零文档**这类**语义问题**无人发现。一个会"除草、补种、调和矛盾"的知识园丁,是平台从"存得下"到"靠得住"的关键。

## 背景与痛点

- F19 查的是**结构**(frontmatter/断链/陈旧);F20 是**写时**去重。**语义层面的矛盾/重复/缺口**完全没人管。
- 典型坏味道无人发现:`design/A` 说"用 JWT"、`design/B` 说"用 session" 却都 active;同一主题散落多篇近似;`src/payment/` 有大量代码却无任何文档(F33 反查为空)。
- 库越大,这类"知识债"越积越多,直接侵蚀 F46 问答与 F47 记忆的可信度。

## 目标 / 非目标

**目标**
- **矛盾检测**:用 F26 语义找"高度相关但结论冲突"的文档对,经 F46 模型判定并给出冲突点。
- **重复聚类**:发现近似文档簇,建议合并(交给 F45)。
- **覆盖缺口**:结合 F33,指出"有代码无文档"的区域,建议补文档(F06 模板)。
- **建议而非自动**:所有改进作为**可审阅建议**进 F22 收件箱;人确认后才动。
- `docky garden`(手动)/ 可由 F55 自治触发。

**非目标**
- 不自动改写/删除(只提建议,执行经 F45/F20/F06 + 人确认)。
- 不做事实正确性裁决(只标"疑似矛盾",由人判定)。

## 用户故事

- 作为维护者,园丁报告"design/A 与 design/B 在鉴权方案上冲突",我据此让其中一篇 supersede 另一篇。
- 作为维护者,园丁指出"支付模块代码多但无文档",我安排补一篇设计稿。

## 交互设计

```
$ docky garden
⚠ 矛盾   design/鉴权改造 ↔ design/旧鉴权:JWT vs session(均 active)
↻ 重复   debug/登录排查 ≈ debug/登录超时(相似 0.86)→ 建议合并(F45)
▢ 缺口   src/payment/* 共 12 文件,0 关联文档(F33)→ 建议补 design
→ 已生成 3 条建议进收件箱(F22),确认后执行
```

## 技术落点

- `src/garden.ts`:语义聚类(F26)+ LLM 矛盾/缺口分析(F46);代码覆盖经 F33 反查。
- 产出**建议条目** → F22 收件箱;执行走 F45(合并/改名)/F20(去重)/F06(补稿)。
- 可被 F55 自治调度;手动 `docky garden`。

## 验收标准

- [ ] 能检出语义矛盾文档对、近似重复簇、代码覆盖缺口。
- [ ] 全部以**可审阅建议**形式进 F22,不自动改动。
- [ ] 确认后经 F45/F20/F06 执行;作用域隔离不变。
- [ ] 分析有单测(语义/LLM 层可 mock)。

## 衡量指标

- 库内 active 矛盾对、近似重复数随园丁运行下降。
- 关键代码区的文档覆盖率上升。

## 风险与依赖

- 误报需可控:给相似度/置信度,人来定夺;绝不自动改。
- 依赖 F26(语义)/F46(判定)/F33(覆盖)/F22(审阅)/F45/F20/F06(执行)。

## 与其他提案的关系(迭代递进)

- 把 **F19 的结构体检** 升级为 **语义级自愈**;与 F19 互补(结构 vs 语义)。
- 是 **F52 评估**之外的另一半质量保障:F52 量化价值,F53 修复内容;可由 **F55 自治**定期运行。
