# F36 · 大库性能与元数据缓存

> 一句话:给文档元数据建一层**按 mtime 失效的缓存**,让 `list`/`search`/仪表盘等不再每次都**全量重读磁盘**,库越大越明显。

## 背景与痛点

随着库变大,**每个操作都在重扫磁盘**:

- `listDocs` 对每篇调 `readDocMeta(full)`,而它 `fs.readFileSync` 整篇来解析标题/frontmatter(`src/core.ts`)——**每次列目录都把所有文件读一遍**。
- `searchDocs` 同样逐篇读全文(`core.ts`);`generateIndex`、F21 仪表盘、F19 巡检、F07 `get_context` 都建立在这次全量扫描上。
- 后果:F02 快速打开的**即输即筛**、F13 检索、`/list` 在几百上千篇时会肉眼可见地卡——而绝大多数文件其实没变。

## 目标 / 非目标

**目标**
- **元数据缓存**:按 `path + mtime` 缓存 `title/status/tags/mtime/链接`(F12),持久化于作用域内(如 `.docky-cache.json`)。
- `readDocMeta`/`listDocs` 先查缓存,**仅重读变化的文件**;缓存失效用 mtime,或挂 F08 提交事件。
- 大结果集**惰性/分批**加载(检索/列表)。
- 缓存对 F26 向量索引可复用(同一套"变更检测")。

**非目标**
- 不改变任何对外数据结构/结果(纯加速,结果一致)。
- 不引入外部数据库(本地 JSON/轻量结构即可)。

## 用户故事

- 作为大库用户,我 `/list`、F02 即输即筛在上千篇时依然跟手。
- 作为维护者,我的仪表盘/巡检秒开,而不是每次全盘重扫。

## 交互设计

```
(无界面变化;表现为"更快")
首次:建立缓存(扫描一次)。之后:仅变更文件被重读。
$ docky cache rebuild     # 需要时手动重建
```

## 技术落点

- 新增 `src/cache.ts`:`{path: {mtime, meta}}`,原子读写(配合 F37);`readDocMeta` 命中即跳过磁盘读。
- 失效:mtime 比对;写/删/移/F08 提交后更新对应条目。
- 缓存文件以 `.` 前缀,排除出 `listDocs`/INDEX(同 F10 trash);`docky cache rebuild` 兜底。

## 验收标准

- [ ] `list`/`search`/index/dashboard 在未变更时不再重读文件内容。
- [ ] 缓存按 mtime 正确失效;写/删/移后对应条目即时更新。
- [ ] 结果与无缓存时**完全一致**(加速不改语义)。
- [ ] 大结果集分批/惰性加载,交互不卡。
- [ ] 缓存不被当作文档;`cache rebuild` 可重建;缓存逻辑有单测与基准。

## 衡量指标

- 千篇规模下 `list`/`search`/dashboard 的耗时下降幅度。
- 重复操作的磁盘读取次数下降。

## 风险与依赖

- 缓存一致性:mtime 兜底 + 提供 rebuild;损坏时安全重建(F37)。
- 复用 F08 提交事件做失效最稳;并发写需原子(F37)。

## 与其他提案的关系(迭代递进)

- **横向提速已交付/在列的扫描类能力**:F01/F02/F13/F19/F21/F26 全部受益。
- 与 **F37** 同属"内功":F36 求快,F37 求稳;缓存读写复用 F37 的原子 IO。
