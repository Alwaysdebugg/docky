# F21 · 知识库洞察仪表盘

> 一句话:给维护者一个**整库鸟瞰**——各类型/状态分布、活跃与陈旧占比、被引用最多的文档、标签热度、健康概览——一眼看清这个知识库长什么样、往哪走。

## 背景与痛点

库在长大,却**没有任何聚合视角**:

- F04 主页是**个人最近/置顶**(按 recency),F19 doctor 是**问题清单**(按 issue),但都不是"整库统计"。
- `generateIndex` 只是**平铺罗列**每篇(`src/core.ts`),看不出"design 有多少、其中多少 active/陈旧""哪几篇被引用最多""哪些标签最热"。
- 维护者想回答"这库健康吗?重心在哪?该清理哪类?"——今天只能逐条数。

## 目标 / 非目标

**目标**
- `docky stats [-p 项目]` + TUI `/dashboard`(亦可作为 F04 主页的"概览"区块):
  - **类型 × 状态** 矩阵计数;active / done / archived / **陈旧(F03)** 占比。
  - **被引用最多**的文档(用 F12 反向链接数排序)、**孤立文档**(无入链)。
  - **标签热度** Top-N(F03 tags)。
  - **近期活动**(F08 提交时间线摘要)。
  - **健康概览**:F19 的 error/warn 计数(点进去看 F19 详情)。
- 纯只读聚合,不改任何文档。

**非目标**
- 不重复 F19 的逐条问题修复(只给计数 + 入口)。
- 不做时间序列图表(终端内用数字/简易条形即可)。

## 用户故事

- 作为维护者,我 `docky stats` 看到"debug 32 篇、其中 9 篇陈旧",决定本周清理。
- 作为团队负责人,我看到"鉴权设计"被 11 篇引用,知道它是核心枢纽,改动需谨慎。

## 交互设计

```
my-app · 概览                                  (共 87 篇)
类型      active  done  archived  陈旧⚠
design      12      4      3        2
debug       18      9      5        9
plan         6      7      1        1
被引用最多  design/鉴权改造 (×11) · plan/路线 (×6)
孤立文档    7 篇(无任何互链)→ 可考虑链接或归档
标签热度    #登录 14 · #支付 9 · #性能 6
健康        ✗1 error · ⚠5 warn   (docky doctor 查看)
```

## 技术落点

- 新增 `src/stats.ts`:对 `listDocs` 结果做聚合(类型×状态、陈旧、标签);被引用排序取自 F12 反链索引;活动取自 F08 `logDoc`/提交;健康计数调用 F19。
- `src/cli.ts` / `src/commands.ts`:`stats` 命令与 `/dashboard`。
- 各依赖缺席时优雅降级(无 F12 则跳过"被引用",无 F08 则跳过"活动")。

## 验收标准

- [ ] `docky stats` 输出类型×状态计数、陈旧/归档占比、标签热度。
- [ ] 展示被引用最多与孤立文档(F12 在线时);展示健康计数(F19 在线时)。
- [ ] TUI `/dashboard` 可查看;数字可点进对应列表(复用 F01)。
- [ ] 纯只读,不修改文档;作用域隔离不变。
- [ ] `src/stats.ts` 聚合逻辑有单测。

## 衡量指标

- 维护者使用 dashboard 后触发的清理/归档动作数。
- 陈旧/孤立文档占比随时间下降。

## 风险与依赖

- 大库聚合性能:复用 `listDocs` 一次扫描,避免重复读文件。
- 依赖 F12(被引用)、F08(活动)、F19(健康);均为可选增强。

## 与其他提案的关系(迭代递进)

- 把 **F03(状态/陈旧/标签)、F12(反链)、F08(活动)、F19(健康)** 的信号**聚合成一个鸟瞰视图**。
- 与 **F04** 互补:F04 是"我最近碰过什么",F21 是"整库现在怎样";二者共同构成完整工作台首页。
