# F44 · Agent 阅读遥测与价值度量

> 一句话:记录 **agent 经 MCP 真正读取/检索了哪些文档**,从而量化"哪些文档真在帮 agent、哪些从没被用过",让维护精力花在刀刃上。

## 背景与痛点

docky 的核心消费者是 **agent**,但**它们读了什么完全不可见**:

- F04 记录的是**人类**的打开(`recordOpen`,`src/core.ts`)。而 agent 经 MCP `read_doc` / `get_context`(F07 已交付)读取/检索文档,**没有任何记录**。
- F21 仪表盘统计的是"有多少篇、什么状态",**不是"哪些被用、哪些没用"**。
- 结果:维护者无从判断**哪些文档真正对 agent 有价值**(高频被检索)、哪些是**死重**(从没被读),清理与优化全凭感觉。

## 目标 / 非目标

**目标**
- **读取遥测**:在 MCP `read_doc` / `get_context` 命中时,按文档记录被读/被检索计数与时间(作用域内、本地)。
- **价值视图**:`docky usage [-p 项目]` / F21 仪表盘区块:**最常被 agent 检索**(高价值)、**从未被读**(候选归档/改写)、检索趋势。
- **联动治理**:为 F03/F19 增信号——"active 但 60 天无人(含 agent)读 → 建议复审/归档"。
- **隐私友好**:只存计数/时间、本地存储、可关闭(F18)。

**非目标**
- 不记录读取内容或 prompt(只记"哪篇被读了几次")。
- 不做跨用户上报/云端分析(纯本地)。

## 用户故事

- 作为维护者,我看到"鉴权设计被 agent 检索 37 次",确认它是高价值文档,优先维护。
- 作为维护者,我看到 8 篇"从没被任何 agent 读过",评估是否归档。

## 交互设计

```
$ docky usage -p my-app
最常被 agent 检索   design/鉴权改造 ×37 · debug/登录排查 ×21
从未被读(候选清理) prompts/废弃话术 · debug/旧排查 …(8)
近 30 天检索趋势    ↑(较上月 +18%)
```

## 技术落点

- `src/usage.ts`:在 `mcp.ts` 的 `read_doc`/`get_context` 命中处埋点;按文档累计计数/末次时间;存作用域内状态文件(复用 F04 state 模式 + F37 原子写)。
- 聚合进 `docky usage` 与 F21 仪表盘;为 F03/F19 提供"久未读"信号。
- 隐私:仅计数、本地、可经 F18 关闭。

## 验收标准

- [ ] MCP `read_doc`/`get_context` 命中按文档记录计数与时间。
- [ ] `docky usage` 展示最常检索 / 从未被读 / 趋势;F21 可嵌入。
- [ ] "active 但久未被读"作为信号供 F03/F19 使用。
- [ ] 可经 F18 关闭;仅本地、不记内容;作用域隔离不变。
- [ ] 埋点与聚合有单测(MCP 命中可 mock)。

## 衡量指标

- "从未被读"文档随治理下降。
- 高价值文档被识别后获得维护的比例。

## 风险与依赖

- 埋点不得拖慢 MCP 读取(异步/批量写,配合 F37 原子)。
- 依赖 F07(get_context)/MCP 读路径;聚合复用 F21;清理信号供 F03/F19。

## 与其他提案的关系(迭代递进)

- 把 **F04 的"人类最近"** 扩展到 **"agent 阅读"** 维度——docky 面向 agent 的独有度量。
- 喂给 **F21**(价值视图)与 **F03/F19**(久未读→复审),让治理**数据驱动**而非凭感觉。
