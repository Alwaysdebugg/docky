# F45 · 批量重命名与安全重构

> 一句话:支持**重命名标签 / 重命名文档 / 整理分类**这类重构操作,并自动修好受影响的互链与引用,让大库的命名随业务演进而不留断链。

## 背景与痛点

F11 给了批量"移动/删除/打标",但**改名/重构无解**:

- F11(已交付)能 `batchMove/batchSetStatus/batchAddTags/batchRemove`(`src/core.ts`),但**没有"把 `#登录` 全库改名为 `#auth`"**这种跨文档重命名。
- **重命名一篇文档会断链**:F12 的 `[[旧名]]`、F04 的最近/置顶、F33 的代码引用都指向旧名,改名后**全断**,无人修复。
- 分类随业务漂移(标签泛滥、命名不一致),却**没有安全重构的入口**,只能手工逐篇改,极易出错。

## 目标 / 非目标

**目标**
- **重命名标签**:`docky rename-tag <旧> <新>`(全库改写 frontmatter 标签,去重合并)。
- **重命名文档**:`docky rename <rel> <新名>`——同时**自动修复** F12 反向链接、F04 最近/置顶、F33 代码引用。
- **安全重构流程**:**预览影响 → 确认 → 一次 F08 提交 → 可 F10 撤销**;支持 `--dry-run`。
- 复用 F11 的批处理与 F37 的原子写,保证整批一致。

**非目标**
- 不改 `DOC_TYPES` 枚举本身(类型重命名属更大改动,先聚焦标签/文档名)。
- 不做正则全文替换(只重构"名称/标签/引用"这类结构化对象)。

## 用户故事

- 作为维护者,我 `docky rename-tag 登录 auth`,全库标签一次统一,无遗漏。
- 作为作者,我把一篇设计稿改名,所有 `[[旧名]]` 链接自动指到新名,不断链。

## 交互设计

```
$ docky rename-tag 登录 auth --dry-run
将影响 14 篇:#登录 → #auth(其中 3 篇已有 #auth,将去重)
$ docky rename design/旧名.md 鉴权改造
✓ 已重命名;修复 6 处 [[..]] 反链、2 处最近/置顶、1 处代码引用(F33);1 条提交
```

## 技术落点

- `src/refactor.ts`:`renameTag`(全库改写 frontmatter,复用 F11 批处理 + F37 原子)、`renameDoc`(mv + 经 F12 反链索引改写所有引用 + 更新 F04 state + F33 引用)。
- 预览:先算影响集再确认;整批 `noCommit` 执行 + 末尾一次 `autoCommitVault`(F08);纳入 F10 oplog 以便 `undo`。
- `src/cli.ts`/`commands.ts`:`rename-tag` / `rename`;`--dry-run`。

## 验收标准

- [ ] `rename-tag` 全库改写并去重合并标签。
- [ ] `rename <rel>` 自动修复 F12 反链、F04 最近/置顶、F33 代码引用,无断链。
- [ ] 重构有 `--dry-run` 预览、确认、单条 F08 提交、可 F10 撤销。
- [ ] 作用域隔离不变;`src/refactor.ts` 有单测(含断链修复)。

## 衡量指标

- 重命名后产生的断链数(目标 0)。
- 标签命名一致性提升(去重后标签总数下降)。

## 风险与依赖

- 引用修复需全面(F12/F04/F33),漏一处即断链——以反链索引为准并测试覆盖。
- 依赖 F11(批处理/SelectableList)、F12(反链)、F04(state)、F33(代码引用)、F08/F10(提交/撤销)、F37(原子)。

## 与其他提案的关系(迭代递进)

- 把 **F11 的批量动作**从"移动/删除/打标"扩展到"**重命名/重构**",补齐大库维护最后一块。
- 依赖 **F12** 反链做引用修复,是其"安全改名"的直接受益场景;改动经 **F08/F10** 可回溯可撤销。
