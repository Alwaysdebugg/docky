# F51 · 多 Agent 协同知识空间

> 一句话:让多个 agent 在同一项目里**共享一块工作记忆**——发布发现、认领/交接任务、看见彼此进展——把 docky 变成多 agent 协作的"共享黑板",而不是各自为战。

## 战略定位(对标 Claude Code 的下一步)

Claude Code 已能跑子 agent / 并行任务。下一道前沿是**多 agent 真正协作**——而协作的前提是**共享的工作记忆与协调层**。docky 天生按项目隔离、MCP 原生、又有 F47 记忆,是这块共享黑板的最佳载体。补上它,docky 就成为多 agent 系统的协调基础设施。

## 背景与痛点

- F47 建模的是**单 agent 的长期记忆**;F22 是**人**审阅;F31 是**异步 git 同步**。**没有任何"多个 agent 实时协同"的层**。
- MCP 当前是**无状态逐次调用**:同一项目上两个 agent 互相看不见——A 已经查明的结论、正在改的文件,B 毫不知情,导致**重复劳动、互相覆盖、结论打架**。

## 目标 / 非目标

**目标**
- **共享会话空间**(作用域内、可隔离):agent 经 MCP 发布结构化条目——`finding`(发现)/`claim`(认领任务)/`handoff`(交接)/`question`——带归属(F31 身份)。
- **彼此可见**:其他 agent `observe`/订阅(复用 F25 资源订阅),据此避免重复、接力推进。
- **任务认领防撞**:`claim` 形成轻量互斥,降低并行覆盖。
- **沉淀**:协同结束把有价值的发现蒸馏为持久文档(F49)或记忆(F47)。

**非目标**
- 不做实时字符级协同编辑(结构化条目级即可)。
- 不替代编排框架(docky 提供"共享记忆/协调",编排仍由上层 agent 框架做)。

## 用户故事

- 作为并行工作的两个 agent,A 发布"已确认根因在 X",B 立刻看到、不再重复排查,直接接手修复。
- 作为编排者,我让 3 个 agent 分头探索,docky 的共享空间让它们认领不同子任务、互不重叠。

## 交互设计

```
# 共享空间(项目 my-app · 协同会话)
[agent-A] claim   修复登录超时
[agent-A] finding 根因:token 刷新竞态(src/auth.ts)
[agent-B] observe → 跳过排查,认领"补幂等测试"
（结束)→ 蒸馏为 debug/登录超时排查(F49)+ 记忆"刷新需加锁"(F47)
```

## 技术落点

- `src/coord.ts`:作用域内共享会话日志(F37 原子追加);条目类型 + 归属(F31)。
- MCP:`coord_post` / `coord_observe` / `coord_claim`;订阅复用 F25;隔离复用 `safePath`。
- 收尾蒸馏到 F49(文档)/F47(记忆)。

## 验收标准

- [ ] 多 agent 可在同一项目共享空间发布/读取 finding/claim/handoff/question(带归属)。
- [ ] `claim` 提供任务互斥,降低重复/覆盖。
- [ ] 其他 agent 可订阅并据此协作(复用 F25)。
- [ ] 协同结果可蒸馏为持久文档(F49)/记忆(F47)。
- [ ] 严格作用域隔离;`src/coord.ts` 有单测(含并发追加)。

## 衡量指标

- 多 agent 任务中的重复劳动/冲突覆盖下降。
- 经共享空间完成的协作任务数。

## 风险与依赖

- 并发写需原子与顺序(F37);避免共享空间变成噪音(条目结构化 + 收尾蒸馏)。
- 依赖 F47(记忆)/F22(沉淀审阅)/F31(归属)/F25(订阅)/F49(蒸馏)。

## 与其他提案的关系(迭代递进)

- 把 **F47 的单 agent 记忆** 扩展为 **多 agent 共享工作记忆**,补齐 docky 的协作维度。
- 协同沉淀回流 **F49/F47**,与 R10 的"问/记/推/录/放"组成多 agent 闭环。
