# F55 · 多模态知识(图/截图/语音)

> 一句话:让架构图、截图、语音备忘成为**可检索、可问答**的一等知识——OCR/描述图像、转写语音,使"找登录流程图""从截图里回答"都成立,而不是把图片当哑附件。

## 战略定位

Claude 本就是多模态的;docky 的知识却还停在纯文本。一个旗舰知识平台应当**理解**团队产出的图与语音,而不仅仅**存放**。把多模态内容纳入检索/问答/记忆,docky 才能覆盖开发知识的真实形态(架构图、白板照、录音决策),与 Claude 的多模态能力对齐。

## 背景与痛点

- F41 把图片/附件**存**进了库,但它们是**不透明的**:F26 语义检索、F46 问答、F13 检索**只对文本生效**。
- 一张架构图的截图,对"搜索/问答"完全隐形;一段语音决策无法被检索;图像里的关键信息(流程、错误栈截图)无法进入 agent 上下文(F07)。

## 目标 / 非目标

**目标**
- **附件即知识**:在 F41 attach 时,经模型(F46,默认 Claude 视觉)对图像做 **OCR + 描述/caption**、对语音做**转写**,生成可检索的**旁挂文本**。
- **纳入检索/问答**:旁挂文本由 F26 索引、F13 命中、F46 可引用作答(标注"来自图 X")。
- **多模态捕获**:粘贴截图/拖入图片即"理解 + 归档";语音备忘转写归档。
- **顺带增益**:生成的描述用作 F39 无障碍 alt-text、F17/F27 导出说明。

**非目标**
- 不做图像编辑/标注画板(只做理解 + 检索)。
- 无视觉模型时**优雅降级**为 F41 纯存储(不报错)。

## 用户故事

- 作为开发者,我搜"登录流程图",命中的是一张截图——因为它的内容已被理解、可检索。
- 作为开发者,我把一张报错截图丢给 docky,F46 能据图中堆栈回答"这是什么错、以前怎么修的"。

## 交互设计

```
$ docky attach design/架构.md ./whiteboard.png
✓ 已附加并理解:OCR+描述 → 旁挂文本(已被检索索引)
$ docky ask "限流是在网关还是服务做的?"
答:网关层。依据:[1] design/架构.md 的架构图(描述:"…网关处限流…")
```

## 技术落点

- `src/multimodal.ts`:在 F41 attach 钩子里调模型(F46 provider,视觉/语音)做 OCR/描述/转写;产出旁挂文本(`.<asset>.txt`,排除出 listDocs)。
- 旁挂文本接入 F26 索引、F13 检索、F46 引用;描述回填 F39 alt-text / F17 导出。
- 模型可配(F18);无模型则仅 F41 存储。

## 验收标准

- [ ] attach 图像/语音时生成可检索旁挂文本(OCR/描述/转写)。
- [ ] 多模态内容可被 F26/F13 检索、被 F46 引用作答(标注来源为图/音)。
- [ ] 描述用于 F39 alt-text 与 F17/F27 导出。
- [ ] 无视觉/语音模型时降级为纯存储(F41),不报错。
- [ ] 提取与索引有单测(模型层可 mock)。

## 衡量指标

- 命中/被引用的多模态内容数(图音从"哑附件"变"活知识")。
- 含图文档的问答可答率提升。

## 风险与依赖

- 提取质量与成本:按需/惰性提取、可配模型、缓存结果(F36)。
- 依赖 F41(附件)/F46(模型)/F26·F13(检索)/F39(alt-text)/F17·F27(导出)/F36(缓存)。

## 与其他提案的关系(迭代递进)

- 把 **F41 的"存附件"** 升级为 **"理解附件"**,让多模态进入 F26/F46/F07 的知识闭环。
- 与 R10/R11 的检索·问答·记忆一脉相承:把知识的**形态**从纯文本扩展到图与语音。
