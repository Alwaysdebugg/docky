# F52 · 知识价值评估回路

> 一句话:用 eval **证明** docky 真的让 agent 更强——同一任务"有 docky 上下文 vs 没有"的对比、检索质量、问答正确率——把"我们觉得有用"变成"这是可量化的提升"。

## 战略定位(Anthropic 式 eval 文化)

Anthropic 靠 eval 驱动一切。一个旗舰知识平台必须能**自证价值**:不能只统计"读了多少"(F44),要回答"**让 agent 的产出变好了多少**"。有了评估回路,docky 的检索/记忆/问答才能被持续、可回归地优化,而非凭感觉。

## 背景与痛点

- F44 度量"哪些文档被读"(使用度)、F19 度量"文档结构是否健康"——**都不衡量结果(outcome)**。
- 没人能回答:"接入 docky 上下文后,agent 完成任务的成功率/步数/正确率提升了吗?""F46 的答案有多忠实?""F26 检索的准召率如何?"
- 改了检索算法(F13/F26)或上下文策略(F07)后,**无法知道是变好还是变差**(无回归)。

## 目标 / 非目标

**目标**
- **结果对比(A/B)**:在任务集上,对比"带 docky 上下文(F07/F46)"与"对照组"的 完成率/步数/正确率。
- **检索质量**:对金标查询集算 precision/recall/nDCG(评 F13/F26)。
- **问答忠实度**:对 F46 答案做 LLM-judge + 引用核对(是否有据、是否臆造)。
- **回归看板**:`docky eval` 输出报告;算法/库变化后可重复跑,追踪趋势。

**非目标**
- 不做模型训练;不外传数据(本地评估、可配模型)。
- 不强求金标完备:支持小样本 + 增量扩充任务集。

## 用户故事

- 作为维护者,我跑 `docky eval`,看到"带 docky 上下文使任务成功率 +22%、步数 -30%",据此决定推广。
- 作为开发者,我改了检索权重后跑回归,确认 nDCG 未下降才合并。

## 交互设计

```
$ docky eval
任务集 24 例 · 模型 claude
  结果对比   成功率 78% → 95%(+17pp)   平均步数 11 → 7
  检索质量   nDCG@5 0.71               答案忠实度 0.93(2 例缺引用)
  对比基线 v1.0-design(F42)→ 检索 +0.04
```

## 技术落点

- `src/eval.ts`:任务/金标集加载;跑"带/不带上下文"两路(复用 F07/F46);打分(确定性指标 + LLM-judge via F46 模型)。
- 检索指标对金标查询评 F13/F26;问答忠实度核对引用(F46)。
- 报告 + 与里程碑(F42)对比的回归追踪。

## 验收标准

- [ ] `docky eval` 产出 结果对比 / 检索质量 / 问答忠实度 报告。
- [ ] 可对同一任务集回归重跑,追踪算法/库变化的影响。
- [ ] LLM-judge 与确定性指标结合;无模型时跑确定性部分。
- [ ] 评估在本地、可配模型;`src/eval.ts` 有单测(judge 可 mock)。

## 衡量指标

- docky 带来的 outcome 提升(成功率/步数/正确率)有数可依。
- 检索/问答质量的回归被及时发现(变差立即可见)。

## 风险与依赖

- 金标构建有成本:支持小样本起步、增量扩充。
- 依赖 F07/F46(被评对象)、F13/F26(检索)、F42(基线对比)、F44(真实使用反哺任务集)。

## 与其他提案的关系(迭代递进)

- 与 **F44 互补**:F44 看"被用",F52 看"有用";共同驱动数据化优化。
